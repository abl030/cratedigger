2026-07-24 (diagnosed from request 8889 Charli xcx "Music, Fashion, Film"): slskd's storage chain is Proxmox host → virtiofs → doc2 → virtiofsd re-export (`microvm-virtiofsd@slskd`) → virtiofs → slskd microVM (192.168.21.2, console via `journalctl -u microvm@slskd`; no guest SSH). File moves incomplete/→downloads traverse FUSE-over-FUSE and fail transiently under load: `System.IO.DirectoryNotFoundException: Could not find a part of the path` (and 3× `Cannot allocate memory` on Jul 22). 61 move failures Jul 22–24 (Vashti Bunyan "Just Another Diamond Day" ×36 across 2 peers, Charli ×21 across 2 peers, singles). A poisoned path stays bad for the rest of that guest boot (Charli failed 13:37→16:56 while Einaudi moved fine), then resolves — inspection always looks healthy. Failures SURVIVED a full doc2 host reboot (Jul 23 14:26), so it is load/race-driven, not accumulated daemon state. Host memory/fds/OOM all clean.

slskd amplifier (reportable upstream bug): the transfer record flips to `Completed, Succeeded` BEFORE the move; a failed move does not revise the state and never emits DownloadFileComplete. Its API serves "all succeeded" for downloads its own task log calls failed. Cratedigger's #146 event-only-location invariant is the containment: materialize refuses (`event_path_never_stamped`), grace window expires after 3600s, request self-heals to `wanted`. Cost is latency only.

Symptom signature for recall: request loops downloading→wanted with "Completed download could not be materialized within 3600s"; `MATERIALIZE FAILED request=<id> reason=event_path_never_stamped` every cycle; slskd events store has ZERO events for the album; all files fully-sized in `incomplete/<album>/`; completed dir exists empty on host; slskd console shows Succeeded-then-move-failure per file.

Reason vocabulary changed in #868 (2026-07-26): the old `MATERIALIZE AUTHORITY FAILED: event_path_missing` line is gone. It fused two causes — this one (slskd never stamped a location, now `event_path_never_stamped`) and "the stamp exists but the file is gone from disk" (now `event_path_gone_from_disk`). Only the FIRST is this virtiofs signature; the second means the move DID happen and something removed the file afterwards. The grace-expiry `download_log` row now carries the reason in `beets_detail`, so the cause survives the journal rolling.

Remediations: (a) quick per-incident: restart `microvm@slskd` to clear poisoned dentries; (b) real fix (nixosconfig infra): move slskd downloads+incomplete off the nested re-export (VM-local disk or direct Proxmox share); (c) upstream slskd issue. Cratedigger owes nothing beyond the #865 message work.

Durable record: nixosconfig#51 (https://git.ablz.au/abl030/nixosconfig/issues/51) — verbose RCA, repro ladder L0-L3, virtiofs exit-strategy options; filed 2026-07-24 via the hermes write:issue token (/run/secrets/forgejo/hermes-token; the nixbot push token 403s on issues). 2026-07-24 attribution deep-dive (post VM+virtiofsd restart 18:47): TWO defects, different owners.
- Defect A (slskd, app-level, provable from its own log, upstream-reportable): flips `Completed, Succeeded` BEFORE the move; on move failure it neither revises state, nor emits the event, nor retries. Turned the infra fault into an API-level lie.
- Defect B (the moves failing — filesystem stack, NOT slskd): slskd successfully CREATES the destination dirs (exist host-side, empty, for Charli + both Vashti spellings) and its source files sit at exactly the paths it wrote — create works, rename fails "part of path not found" per-album-sticky for hours while other albums interleave fine; ENOENT+ENOMEM flavors; recovers when idle; recurs across full host reboots. Mechanism hypothesis: FUSE-over-FUSE inode instability — outer Proxmox virtiofs renumbers/evicts inodes under doc2-side churn (cratedigger's 5-min tree walks are a churn source), the re-export virtiofsd's inode map goes stale, guest gets sticky ENOENT on one dentry (incomplete/<album> shared by all its files).
- The Jul 23 Vashti failures were downloads NO cratedigger request owns (req 1092 history is all-April) — trigger is not cratedigger's enqueue pattern.
- Repro ladder (bisect the guilty layer): invariant "mkdir D; slow-write F under I with fd held open minutes; rename I/F→D/F never ENOENTs"; harness = N concurrent slow-writers with randomized dirs; antagonist one layer below = getdents/stat sweeps + page-cache pressure. L0 Proxmox-local (clean sanity) → L1 doc2 /mnt/virtio single-nest → L2 throwaway microVM with re-export (production topology; expect dirty) → L3 real slskd on VM-local disk (acquits/convicts slskd). Passive alternative: virtiofsd debug logging + wait for recurrence; live canary = request 8889's next grab post-restart.
