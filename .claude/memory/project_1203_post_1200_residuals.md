2026-08-20: issue #1203 CLOSED — PR #1220 merged (`f72b1f4f`), nixosconfig pin `bab02532`, deployed and cycle-verified. Residuals filed as #1221. Durable detail lives in `docs/beets-primer.md`, `docs/jellyfin-primer.md`, `docs/plex-primer.md`, and `docs/solutions/perceptual-hashing-cannot-judge-cover-art.md`.

Durable gotchas:

- **`nix flake update <input>` follows the input's BRANCH TIP.** `cratedigger-src` carries no ref, so the pin helper could only ever produce main's current tip, and any older target was physically unproducible — that, not receipt state, was the #1203 deadlock. `scripts/pin_nixosconfig.sh` now pins the exact requested rev via `nix flake update cratedigger-src --override-input cratedigger-src github:<owner>/<repo>/<rev>`, deriving owner/repo from flake.lock's own `original` node. Verified live: `original` is left untouched so it does not poison later ordinary updates, and an unmerged branch commit *does* resolve — which is why the deploy skill, not the script, owns the "is it merged" check.
- **Jellyfin can NEVER reap an album whose directory vanished, by design.** Deletion is computed during the **parent** folder's validation (`Folder.ValidateChildrenInternal2`, a set difference over the parent's children), so an item cannot delete itself. Worse, that method's `IOException` arm logs *without returning*, so refreshing an album whose directory is gone proceeds with an empty disk view and **deletes that album's own child rows** — measured: a probe refresh removed 17 `Audio` rows. Never "just refresh" a stale Jellyfin item. Plex by contrast genuinely self-heals via a nearest-existing-ancestor partial scan.
- **Jellyfin's own NFO writes resurrect vanished paths.** The music union is `media_metadata/Music=RW:Music=RO` with `SaveLocalMetadata: true`, so a renamed album leaves a metadata-only directory in the RW branch that keeps the OLD path alive through the union — the album never looks vanished. Explains union 8,588 dirs vs source 8,555. Tracked in #1221.
- **A failed `fuse-mergerfs-music.service` silently blinds Jellyfin for days.** Its `ExecStartPre=test -w /mnt/virtio/media_metadata/Music` fails when that directory's group drifts from `users` to `nogroup` (the unit runs with `Group=users`); Jellyfin's library-root fail-safe then aborts validation of the entire music tree on every scan **while still reporting `Status: Completed`**. Nothing was ingested 2026-08-16 → 2026-08-20. Diagnose with `GET /Environment/DirectoryContents?path=<library root>` — the exact predicate Jellyfin's own `IsAccessible` uses. Fix on prom (unprivileged LXC, owner shows `nobody`, so chgrp from inside the container fails), then `systemctl reset-failed` + start.
- **`postflight.replaced_albums` reports ONLY dup-guard removals**, so it structurally cannot report a directory that left the library any other way — that, not "staleness", is why it needed a Beets before/after directory snapshot as the primary source. `album_path == imported_path` is the CORRECT value for an ordinary same-path upgrade; do not read it as a defect.
- **Three consecutive correction rounds each shipped a NEW false claim**, each caught only by the next independent read: a corpus statistic that did not measure the defect it was cited for, its replacement citing a `download_log` row that an earlier row for the same request refutes, and a journal recipe naming the wrong systemd unit. Reinforces [[correction-rounds-mint-false-claims]]; the new part is that a claim written to *replace* a discredited one is the highest-risk sentence in the series — re-derive it, do not sanity-check it.
- **`journalctl -u cratedigger` does NOT cover the importer.** Post-import notifier and reconciler logs (`JELLYFIN PIN: captured`, `MEDIA SERVER RECONCILE:`) come from `cratedigger-importer.service` — measured 0 vs 16 occurrences over 14 days.
- Two tests fail under **another session's** concurrent gate on doc1, not only at high worker counts. The `run_suite` admission lock serializes suites but not their non-suite phases. Do NOT build a load-floor poller around the gate — the lock already queues; see #1156 item 6. One of the two was misattributed here: `test_node_jsonl_worker`'s readline timeout is a genuine timing budget, but `test_daily_flake_update`'s process-group signal test was reading a file the subprocess under test had just truncated — `Path.write_text` opens for truncate, so the poll loop caught it EMPTY, and the `JSONDecodeError` said `char 0` all along. PR #1327 fixed it with an atomic write; load only widened the window.
